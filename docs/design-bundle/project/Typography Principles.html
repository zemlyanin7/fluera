One book.
Six scripts.
Six typefaces.

A font designed for English does not read well in Japanese. A font that flatters Cyrillic loses Arabic's calligraphic rhythm. Fluera treats typography as a property of the language, not the app — every script gets the typeface it was drawn for.

01
Principle one

The script chooses the font, not the brand.

Brand consistency is achieved through tone — proportion, contrast, warmth — not through forcing one font family across scripts it was never drawn for. A "universal" font does not exist; what exists is a universal feeling, executed locally in each writing system.

✗ A single font for all
蒼白い十月の朝、潮は誰の記憶よりも遠くへ引いた。
Latin-first fonts fall back to system Japanese — letters from different families, mismatched weights, broken rhythm.
✓ Native pairing
蒼白い十月の朝、潮は誰の記憶よりも遠くへ引いた。
Shippori Mincho B1 — kanji and kana from one designer's hand. Even color, even rhythm, even soul.
02
Principle two

Two roles, two faces, per language.

Every language gets exactly two fonts: a reading face for body text inside books and translations, and a UI face for chrome — buttons, labels, captions. The reading face has personality; the UI face gets out of the way.

Why these. For Latin and Cyrillic we use independent families — they happen to harmonise. For CJK, Arabic, and Devanagari we use families designed expressly for those scripts by people who write in them. Falling back to a "universal" sans here would erase the difference between reading and decoding.

03
Principle three

Metrics travel with the script.

These are not aesthetic preferences — they are required for legibility. Setting Japanese at Latin's 1.65 makes kanji collide; setting Arabic at 1.6 chokes the descenders. The metric is part of the font choice.

04
Principle four

Mixed scripts get mixed type.

When a Japanese word appears next to its Russian translation, each side is set in its own pairing. The translation sheet is not "one font with a fallback" — it is two carefully composed columns, sharing only color, rhythm, and the moment of meaning between them.

Direction flips with the script (Arabic right-to-left, Russian left-to-right). The font flips with the script. The layout grid stays. Familiarity comes from the system, not from forcing one shape onto all.

05
Principle five

One attribute switches everything.

The whole system is driven by a single declarative hook: data-lang="ja" on any element. CSS custom properties cascade down — reading font, UI font, line-height, tracking, direction. A designer never picks a font by name; they pick a language. 

/* tokens.css */
[data-lang="ja"] {
  --font-reading: "Shippori Mincho B1", serif;
  --font-ui:      "Noto Sans JP", sans-serif;
  --reading-leading:        1.85;
  --reading-letter-spacing: 0.02em;
}

[data-lang="ar"] {
  --font-reading: "Amiri", serif;
  --font-ui:      "Noto Sans Arabic", sans-serif;
  --reading-leading:        1.95;
  direction:                rtl;
}
<!-- usage -->
<article data-lang="ja">
  <h1>八岐の園</h1>
  <p>蒼白い十月の朝、潮は…</p>
</article>

Components consume the variables — never a font name. A translation sheet that shows a Japanese word above a Russian gloss is literally two nested elements with different data-lang; the system handles the rest.

06
Principle six

What we will not do.

  • No webfont everywhere. We will not load 14 MB of fonts on every screen "just in case." A screen requests the fonts for the languages it actually shows.
  • No fallback chains pretending to be design. font-family: "Inter", system-ui for Japanese is a bug, not a design choice. Either we have the right font, or we say so.
  • No transliteration in body text. Russian books stay Cyrillic. Japanese stays kanji + kana. The user is learning a language; we do not pre-Latinise it for them.
  • No mixing a serif with a different studio's "sans" sibling on a whim. Pairings are chosen and tested together. Substitutions go through a typographer, not a settings panel.
